# MedCore 健康科普：背景、规划与架构

> 状态：设计草案 · 2026-11-02  
> 范围：第一阶段仅建设健康科普问答；症状问诊、报告解读等属于后续独立业务。本文描述目标架构，不代表所有模块已经实现。

## 1. 项目背景与定位

MedCore 已具备用户认证、会话与消息持久化、独立 RAG 检索服务、DeepSeek 回答和 SSE 流式输出。当前链路能回答健康知识问题，但仍是固定流程：取最近 12 条消息作为模型历史，只用本轮原始问题检索本地知识库，然后将片段交给模型生成回答。

目标是以现有链路为基线，逐步引入 **LangGraph + 单 Agent + 有界工具调用循环**：模型可以在受控范围内选择本地检索、联网搜索或补充检索，但工具权限、调用上限、医疗安全和失败降级仍由代码约束。健康科普尤其需要处理多轮追问、知识时效、资料不足、引用错误和用户把症状问题发进科普入口的情况。

检索结果的可追溯性是必要的；独立的 `EvidenceService`、每轮一次的 LLM `EvidenceEvaluator` 不是预设前提。先保留来源元数据并评测真实问题，再决定是否增加专门核查环节。

产品定位是**提供有来源的健康知识解释，帮助用户理解医学信息**；不提供确定性诊断、处方、个体化治疗决策，也不把科普问答宣传为经过临床验证的分诊系统。

### 当前实现与目标的边界

| 能力 | 当前状态 | 第一阶段目标 |
| --- | --- | --- |
| 前端、认证、会话、SSE | 已实现 | 保持接口兼容，改善过程状态与来源展示 |
| 本地知识库检索 | 已通过独立 RAG HTTP 服务接入 | 保留现有服务，将返回值适配为可追溯的检索文档 |
| 多轮上下文 | 最近 12 条消息用于生成；检索只用当前问题 | 补全指代、控制上下文预算、避免追问检索失焦 |
| 联网搜索 | Tavily 试验函数，尚未接入聊天链路 | 按需搜索、读取关键页面并核对出处与时间 |
| 检索结果与引用 | 本地片段编号进入提示词，原始来源存入消息 | 最小 `RetrievedDocument` 契约、后端编号、来源可追溯 |
| LangGraph | 尚未接入 | 先保留固定链路基线，再引入本地检索工具与有界单 Agent 循环 |
| 症状问诊 | 尚未实现 | 不纳入本阶段交付 |

## 2. 第一阶段目标与非目标

### 目标

1. 普通健康科普问题优先使用本地知识库，输出易读、有依据的中文回答。
2. 对“它有什么作用”等追问，结合本会话历史形成独立检索问题，同时保持用户原意。
3. 对明显依赖近期信息、药物状态或本地资料过时/不足的问题，按策略补充联网核查；没有核实到资料时明确说明。
4. 本地与网页检索结果采用最小共同格式，统一编号与展示；引用可以追溯到实际来源。
5. 保持现有会话权限、SSE 基本事件和“完整回答成功后再保存”的语义。
6. 建立可重复的检索、回答、引用、安全和故障评测集，作为增加复杂度的依据。

### 非目标

- 不在本阶段实现症状动态追问、诊断建议、急诊分诊结论、药物剂量计算或报告解读。
- 不让模型无限循环检索，也不让网页内容直接决定系统指令；不要求每轮都运行独立的 LLM 证据评估。
- 不因节点数量多而认为答案更可信；资料冲突优先从数据质量、检索和评测中定位原因。
- 不要求所有问题联网，不因引入 LangGraph 而重写 RAG 服务、数据库或前端。
- 不预设必须换用 LangChain 的模型封装；LangGraph 节点可以继续调用现有 DeepSeek SDK 适配层。

## 3. 目标架构

```text
Vue 3 健康科普入口
       │ 提问、会话 ID
       ▼
FastAPI：认证、会话鉴权、SSE 协议
       │
       ▼
services/chat.py：单轮事务与工作流编排
       │
       ▼
Education Graph
  代码级安全边界 → 有限历史/上下文构建
                         │
                         ▼
            ┌─────────────────────────────┐
            │ DeepSeek 单 Agent（受限循环） │◀──────┐
            └──────────┬──────────────────┘       │
                       │ 工具调用                  │ 检索结果 + 来源
                       ▼                           │
             本地 RAG / 按策略 Web Search / 读取网页 ─┘
                       │
                  Agent 完成回答
                         ▼
       回答生成 → 引用对应与安全边界检查
       │
       ▼
repositories/chat.py：MySQL 保存完整问答与来源
       │
       └── SSE：status / delta / done / error
```

第一阶段只有健康科普模式，无需额外的 LLM 业务 Router。这里的“单 Agent”只负责科普工作流内的检索工具选择，不负责决定业务模式，也不负责独自做医疗安全决策。将来加入症状问诊时，由前端显式选择模式，后端按**会话中持久化的模式**路由到独立工作流；前端选择不能替代每个工作流的安全检查。旧会话的模式迁移策略需在第二个模式上线前确定。

### 模块职责与建议落点

| 模块 | 职责 | 建议位置 |
| --- | --- | --- |
| API | 鉴权、参数校验、SSE 转发；不承载检索决策 | `api/chat.py` |
| 对话服务 | 读取历史、运行工作流、成功后保存、协调错误 | `services/chat.py` |
| 科普工作流 | 单 Agent 与工具调用循环，代码控制工具权限、次数和终止条件 | 规划中的 `workflows/education/` |
| 上下文处理 | 追问补全、历史裁剪和 token 预算；先作为工作流内函数实现 | 需要时再拆分 |
| 检索文档适配 | 将不同工具的结果转成最小共同格式，去重、截断并分配引用编号 | 规划中的 `schemas/retrieval.py` 与轻量适配函数 |
| 本地检索 | 调用独立 RAG 服务；不把整个 Milvus 栈搬入 API 进程 | `rag/pipeline.py` |
| 联网能力 | Tavily 调用、关键网页读取、超时与结果限制；不在导入时创建必须配置的客户端 | `capabilities/web_search/` |
| 科普 Prompt | 回答组织、知识使用、引用与安全边界 | `workflows/education/prompts.py` |
| 模型适配 | DeepSeek SDK 调用与流式文本；不承载业务提示词 | `llm/client.py` |
| 持久化 | 会话和消息的 MySQL 读写、所有权检查 | `repositories/chat.py` |

## 4. 核心数据契约

在写工具与图之前，先约定最小输入输出；它只是跨本地 RAG、网页搜索和引用展示的数据契约，不是独立的证据管理系统。具体实现可用 Pydantic、TypedDict 或 dataclass。

### 4.1 单轮输入与工作流状态

- 输入：`session_id`、`question`、受限历史；`user_id` 来自鉴权上下文，不信任客户端传入。
- 过程状态：必要的模型/工具消息、可选的独立检索问题、检索文档、工具调用次数、错误/警告和最终回答。
- 输出：回答正文、可展示的引用来源、回答状态（完成或明确失败）。

图状态应保存完成当前轮和必要重放的信息，不应无上限复制完整会话、网页正文或密钥。检索策略和安全边界可在代码中执行，不必都变成 LLM 分类节点。数据库消息是用户可见对话记录的事实来源；若以后需要 checkpoint，它只负责工作流恢复，不能成为第二套相互矛盾的聊天历史。

### 4.2 最小检索文档 `RetrievedDocument`

建议字段：`id`、`content`、`source`、`kind`（`local`/`web`）、`title?`、`url?`、`published_at?`、`retrieved_at?`、`score?`。缺失的网页发布日期保持为空。后端在去重、截断后分配本轮引用编号；把实际用于回答的文档来源保存到消息 `sources`，并让前端能展示对应链接或资料名称。

本地检索分数和 Tavily 分数不可直接横向比较；相关性也不等于医学可信度。不得把检索时间冒充发布日期。网页摘要只用于发现资料，涉及关键医学事实时应读取原文并核对适用范围。统一格式是为了避免直接拼接两家工具的原始响应，不要求额外调用 LLM 为每篇资料打分。

## 5. 健康科普工作流设计

### 基线：保持现有固定 RAG 链路

`读取/裁剪历史 → 本地检索 → 整理片段 → 生成回答 → 返回结果`。

先保留这条链路作为对照，并补齐代表性测试题、来源格式和故障测试。引入 LangGraph 时应保持现有 API、SSE、会话权限及成功后保存的语义，允许通过开关回退到基线。它不是最终目标，也不要求先建立多个独立的 LLM 节点。

### 目标：受限的单 Agent 工具循环

1. 用有限历史构造当前轮上下文。对于“它有副作用吗”等追问，Agent 可形成独立检索词，但不得改变用户本意；无法消歧时应询问或说明不确定性。
2. Agent 只可调用经过后端注册的工具：本地知识库检索、联网搜索、必要的网页读取。除寒暄或澄清外，医学事实回答须有可追溯资料；普通科普问题优先查本地资料，时效性问题允许或要求联网核查。这些策略不能只靠模型自觉遵守。
3. 工具返回 `RetrievedDocument`。适配函数负责去重、截断、记录来源和分配引用编号；不为此预设独立 `EvidenceService`，也不要求每次额外运行 LLM 证据评估。
4. Agent 可在资料不足时补充检索，但必须设置最大模型轮次、工具调用次数、联网请求数、总时长和费用上限。达到上限仍无法支撑答案时应明确说明。
5. 最终回答必须保留可追溯引用；后端至少检查引用编号能对应已返回的来源。网页正文和检索片段始终是低信任资料，不能覆盖系统提示或安全规则。流式输出前是否需要缓冲引用，须按第 7 节的兼容策略确定。

单 Agent 是一种**待验证的实现选择**，不是医疗正确性的保证。要用同一组问题比较固定链路与 Agent 版本的追问表现、引用准确率、时效性、延迟和费用；若没有可测收益，保留更简单的路径。后续若坏例子集中在新旧资料冲突，再有针对性地改进知识库、检索或增加核查步骤。

## 6. 失败、安全与隐私策略

| 情况 | 预期处理 |
| --- | --- |
| 本地检索失败 | 将工具错误反馈给工作流并标明知识库不可用；只有满足联网策略且可核实来源时才考虑降级，不静默当成“没有资料” |
| 网页搜索/读取失败 | 普通静态问题可继续使用充分的本地证据；依赖最新事实的问题不得伪装成已完成核查 |
| 没有足够资料或资料冲突 | 表达无法确认或存在分歧，不生成确定性医学结论；不把 Agent 的自信判断当作核实结果 |
| 模型超时、流式中断 | 发送可识别的错误事件，不将半截回答保存为完整回复；保留重试能力 |
| 引用编号无对应来源 | 检查编号是否存在，不将其保存为正常完成的可信引用；若流式内容已发出，发送错误状态并记录事件，不能承诺撤回 |
| 工具循环超过预算 | 停止后续调用；基于已核实资料作有限回答或说明无法确认，不无限重试 |
| 明显急症或诊疗请求 | 提供安全引导、说明科普边界，不输出诊断或处方 |

用户问题可能包含病史、联系方式等敏感信息。联网查询只发送完成检索所需的最少内容；外部搜索与日志均避免泄露身份信息、API Key 和完整敏感对话。引入 checkpoint 时再明确加密、保留期限、删除会话时的同步清理及用户隔离。重试与补检索应有幂等约束，防止重复保存一轮回答。

## 7. 兼容、观测与评测

- 对外继续沿用现有聊天接口及 `status`、`delta`、`done`、`error` SSE 事件；新增阶段可通过 `status.phase` 扩展，但应保持旧前端可用。成功完成后再保存问答和来源。
- 流式 `delta` 一经发出就无法撤回。若采用“生成完再检查引用”，只能阻止保存或标记错误，不能保证用户未看到错误引用；严格引用模式需在发送前缓冲回答，或将引用展示延后到 `done` 时由后端校验后统一下发。两种方案要权衡首字延迟和体验。
- 记录每轮的工具选择、调用次数、资料来源类别、耗时、异常类型和 token/费用估计；日志中不记录原始敏感内容或密钥。
- 建立最小测试集：普通科普、多轮指代、最新知识、旧资料冲突、无证据、伪造引用、网页提示注入、明显风险表达、RAG/Tavily/LLM 故障、SSE 中断及跨用户会话访问。
- 指标至少覆盖检索命中、工具选择正确率、引用可追溯率、答案有依据比例、时效问题核查、风险表达处理、P95 延迟及失败率。先记录固定链路基线再定阈值，不以模型自评分替代人工抽检。

## 8. 实施顺序与验收

| 阶段 | 交付 | 验收重点 |
| --- | --- | --- |
| 0. 契约与基线 | 最小 `RetrievedDocument`、故障分类、代表性测试题，保留固定链路 | 现有接口与聊天测试持续通过，记录质量/延迟基线 |
| 1. 本地检索单 Agent | LangGraph 中注册本地 RAG 工具，设调用上限与回退开关 | 普通、流式、失败、保存和用户隔离与旧行为兼容；工具选择可追踪 |
| 2. 上下文与引用 | 追问补全、预算控制、来源编号和引用检查 | 多轮检索优于基线；错误引用可被发现 |
| 3. 条件联网 | Web Search、关键页面读取、隐私最小化、失败降级 | 过时问题能补充资料；搜索失败不假称已核实 |
| 4. 受限补检索 | 仅对资料不足问题允许再次调用工具，设置轮次与费用限制 | 相比阶段 3 的评测有可测改善；延迟/费用可接受 |

症状问诊另立设计文档和安全评测；在科普流程稳定前，不把它混入同一张图。若第二业务模式落地，再为会话新增并迁移持久化的 `mode` 字段，并设计独立的 Symptom Graph 与暂停/恢复协议。

## 9. 待确认的设计决策

1. 哪些来源可用于医学时效核查？是否需要按主题维护来源白名单与地域适用范围？
2. 用户是否有“仅本地资料 / 允许联网”开关？默认策略和隐私告知如何展示？
3. 第一阶段是否需要持久化 graph checkpoint？单轮科普可先沿用 MySQL 会话历史，不因使用 LangGraph 就默认引入另一套历史；症状追问上线前必须确定 `thread_id`、恢复、取消与存储方案。
4. Web Search、模型和检索服务分别允许的超时、次数、费用预算是多少？
5. 哪些测试题由具备医学背景的人员审阅，哪些只用于技术回归？
6. 当前选用的 DeepSeek 模型和 SDK 是否满足工具调用与流式事件需求？若不满足，是否保留固定链路作为回退？
